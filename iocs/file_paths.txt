# StyleSmuggler / CVE-2026-75650 — filesystem, process, and cron indicators
# Sources: Sansec advisory (updated through at least 2026-09-14 13:27 UTC) + Adobe
# APSB26-146 + community IR on confirmed live infections. See docs/VULNERABILITY.md for
# the full build-by-build comparison, the second attacker's technique, and the third,
# framework-level toolkit.

## Implant binary and lock files — THREE known builds so far, all believed to be the
## same Rust codebase (the Rust implant campaign; a SEPARATE, unrelated PHP web-shell
## attacker is covered further down). Check every account's home directory on shared
## hosting, not just root's or the webroot.

# gvfsd-user build (first seen 2026-09-04, process [kworker/u:8:0])
~/.local/share/.gvfsd/gvfsd-user
~/.local/share/.gvfsd/.gvfsd_<8hex>.lock
/tmp/.gvfsd_<8hex>.lock          # second lock location, outside the home dir
/tmp/.kw_<random><random>

# fc-cache build (first seen 2026-09-06, version 2.1.4, process fc-cache — arm64 and x86-64 builds)
~/.cache/fontconfig/fc-cache
/tmp/.fc_<8hex>.lock             # <8hex> is the first half of the implant's agent ID
/tmp/.fc-<8hex>/fc-cache         # variant: hyphenated subdirectory
/tmp/fc-cache                    # variant: dropped directly in /tmp, no subdirectory
/tmp/.cache_<random>             # variant naming seen alongside fc-cache drops

# chronyd build (first seen 2026-09-07, version 2.1.5, process chronyd — observed
# re-dropped on a host already running the fc-cache build, with the SAME agent ID and
# incremented version: same operator, new disguise)
/tmp/.chrony-<8hex>/chronyd
/tmp/.gvfsd-<random>             # variant naming seen alongside chronyd drops (hyphen, not underscore — distinct from /tmp/.gvfsd_<8hex>.lock above)

## Cron persistence — written DIRECTLY to the spool file, not via `crontab`, so it does
## not generate the REPLACE line syslog normally logs on a crontab change.
## File: /var/spool/cron/crontabs/<user>
*/5 * * * * exec <home>/.local/share/.gvfsd/gvfsd-user   # gvfsd-user build: every 5 min
*/5 * * * * exec /tmp/.kw_                                # variant seen pointing at /tmp directly
13,43 * * * * <home>/.cache/fontconfig/fc-cache >/dev/null 2>&1   # fc-cache build: twice/hour — easy to miss
57,27 * * * * /tmp/.chrony-<8hex>/chronyd >/dev/null 2>&1         # chronyd build: twice/hour, different offset
# Observed duplicated up to 1728 times in one crontab; self-restores within ~1 second of
# manual removal if the process/binary itself hasn't been cleaned first. Clean order:
# persistence -> process -> binary -> re-check persistence after a full cron cycle.
# IMPORTANT: the chronyd build has also been observed relaunching with NO cron entry at
# all — an empty crontab is NOT proof of a clean host. In the specific observed case,
# the relaunched chronyd process's PARENT PID WAS 1 (i.e., it had been re-parented to
# init/PID 1 after its original parent exited) and it reported an incremented version
# in its beacon (2.1.5, up from 2.1.4 for the Sept 6 build) — consistent with the
# process having relaunched/renamed ITSELF rather than being restarted by cron. Do not
# rule out this implant on cron-absence alone; check `ps -eo pid,ppid,user,comm` for a
# `chronyd` (or other masquerade name) entry with PPID 1 that ISN'T your system's
# actual NTP daemon, alongside the hash/ownership checks elsewhere in this file.
# Also check for other persistence mechanisms (systemd user timers, shell startup
# files, PHP auto_prepend_file) below.

## Failed cron-write indicator — on hosts where the web/site user isn't permitted to
## write a crontab, the implant's repeated attempts can leave a distinctive log trail:
grep -Rni 'crontab command not allowed' /var/log/ 2>/dev/null
# Repeated hits for the Magento/web-server user are a strong reason to investigate
# further even if you find no cron entry or dropped binary.

## Other persistence mechanisms to check — not confirmed StyleSmuggler-specific, but
## standard places an attacker with the site user's code-execution would plant a
## fallback, and worth ruling out before declaring a host clean:
~/.config/systemd/user/                # user-level systemd timers/services
/etc/cron.d/ /etc/cron.hourly/ /etc/cron.daily/ /etc/cron.weekly/ /etc/cron.monthly/
~/.ssh/authorized_keys                 # check every key is accounted for
~/.bashrc ~/.bash_profile ~/.profile ~/.zshrc     # check for curl/wget/base64/tmp-path additions
.user.ini / .htaccess / php.ini        # check for injected auto_prepend_file / auto_append_file

## Process masquerade — three known disguises, all legitimate-sounding system process
## names. Check OWNERSHIP (non-root uid) and, where possible, compare against the real
## system binary at the equivalent path — the name alone proves nothing.
[kworker/u:8:0]     # gvfsd-user build — real name of a Linux kernel worker thread
fc-cache             # fc-cache build — real name of the fontconfig cache utility
chronyd              # chronyd build — real name of the NTP daemon on most distros

## Second, independent delivery vector for the SAME Rust-implant campaign (confirmed
## 2026-09-05/06): a file uploaded through Magento's CUSTOMER CUSTOM OPTIONS feature,
## used as the write primitive instead of the log-poisoning path below. Confirmed to
## succeed even when session storage has been moved off Redis — that mitigation alone
## does not close this path. No specific upload path has been publicly confirmed as of
## this writing; treat any unexpected file appearing in customer-custom-options-related
## storage as suspect and watch for Sansec/community updates on the exact location.

## Poisoned files (check BOTH — community responders' confirmed infections came
## through system.log, which the original advisory's own quick-check command does not cover)
var/log/system.log       # poisoned via an invalid store code, logged verbatim by Magento
var/report/<hash>        # the location the original advisory's quick-check targets

## Request signature (exploit delivery, as observed in the wild)
POST /graphql?styles[...]=                                                  # percent-encoded in the wild
POST /paypal/transparent/response/?<?=eval(base64_decode('...              # published by Sansec
# Also observed riding in the User-Agent header rather than the URL on requests to:
GET  /customer/section/load/?sections=customer&force_new_section_timestamp=true

## Access-log grep keywords (broader than styles[] alone — from corroborating community
## sources). Test on your own logs first: both patterns below can in principle match a
## storefront search for that literal text, though this returns 0 hits on almost every
## real store.
grep -acE 'styles(\[|%5B)|generatorClass|with_resolved|cdnflare' access.log
grep -acE 'styles(\[|%5B)|(\{\{|%7B%7B)(block|config|var)' access.log        # narrower variant
grep -c '"POST /graphql'  access.log                                         # baseline: do you even use GraphQL?

## Trigger header (value is regenerated per request — match the SHAPE, not the literal value)
X-TRACE-<10 hex>     # e.g. X-TRACE-1713CB9C2F   — observed morning of 2026-09-05
X-<12 hex>           # e.g. X-52988DAECE51, X-4427457CBAC9 — observed afternoon of 2026-09-05, TRACE dropped entirely
# A detection pinned to "X-TRACE-" alone goes blind against the second family. This
# changed once within 24 hours of disclosure; assume it can change again.

## Response marker (proof of execution, not just that the payload was sent)
MG<20 hex>::<base64 result>::/MG<20 hex>
# e.g. MG8a5ee8fd94fdb9fc6b50::...::/MG8a5ee8fd94fdb9fc6b50 — hex differs per request, match the shape
#
# IMPORTANT: this is NOT the only "MG"-prefixed marker family. The execution-without-
# email chain (see the THIRD-TOOLKIT section further down) uses fixed-string markers
# that don't fit the hex-shape regex above: "MGPROOF::" and "MGKWSIM::". A detection
# tuned only to the hex-shaped MG<hex>:: pattern will miss both — grep for the literal
# "MGPROOF::" and "MGKWSIM::" strings too, not just the regex.

## User agents on the exploit requests (never a real browser)
python-requests 2.15.0      # first wave — note the SPACE, not a slash
python-requests/2.32.4      # second wave
# Version changed between waves. Treat "python-requests on POST /graphql with a styles[]
# argument" as the signal, not any specific version string.

## Early-warning indicator — no tooling required, check your inbox
# A garbled "Payment Transaction Failed Reminder" email containing raw, unrendered
# {{var ...}} template tags, sent to/from a customer address ending in ".invalid". This
# is a side effect of the exploit's detonation stage and is often the FIRST visible
# sign of exploitation, ahead of any log-based indicator. An unexpected burst of
# failed-payment notification emails is also worth investigating, though legitimate
# card declines cause these too.

## Network behavior anomaly (not file/process, but worth flagging alongside these)
# One confirmed infection made a local Redis connection burst instead of any outbound
# traffic: ~28 simultaneous connections to 127.0.0.1:6379, reading Magento session data
# directly out of the store's own Redis instance. The fc-cache/chronyd build instead
# beacons over UDP/123, disguised as NTP traffic, and separately makes plain-HTTP calls
# to public IP-lookup services with a truncated User-Agent — see domains.txt for both.
#
# IMPORTANT: don't assume Redis is only ever on port 6379. At least one confirmed
# investigation found the store's Redis instance running on a non-default port
# (21113 in that case) — always read the actual host/port out of
# app/etc/env.php's cache and session configuration blocks rather than
# hardcoding 6379 in your own checks:
grep -nA40 "'cache'" app/etc/env.php
grep -nA30 "'session'" app/etc/env.php

## A SECOND, UNRELATED ATTACKER (confirmed 2026-09-07) — different operator, same
## StyleSmuggler entry point, much simpler payload. See docs/VULNERABILITY.md for the
## full technical breakdown. Do NOT assume cleaning the Rust implant above makes a
## store clean — check for this independently.

## Web shell path (the dropper, ~485 bytes, PHP) — pub/media should NEVER contain
## executable PHP on a correctly configured Magento store, so any hit here is significant
pub/media/catalog/product/cache/ss_<10hex>/sync_<10hex>.php
# Detection — use a broad glob (*.ph*) to also catch .phtml/.phar variants, not just
# literal .php:
find pub/media -type f -name '*.ph*'

## Web-shell authentication gate — the dropped shell only responds when a specific
## request header is present; without it, requests return a generic 404, which is
## exactly why filesystem discovery (the find command above) matters more than trying
## to probe the shell over HTTP. Published header/value pair (2026-09-09 Sansec IOC
## update):
X-Cache-Token: fced27f6d57702565353ecc11722533b
# This is presented here PURELY as a log-grep signature for identifying requests that
# targeted a dropped web shell in your access logs — do not send this header to a
# suspected shell path to "test" it; that interacts with live malware. Use the
# filesystem/hash checks instead to confirm presence, and your access logs (grep for
# this header value) to see whether it was ever successfully invoked.
grep -c 'X-Cache-Token: fced27f6d57702565353ecc11722533b' access.log

## Recon probe (sent BEFORE the dropper, from the same operator) — a cover GraphQL
## query with the real payload smuggled in the Store: request header instead of the
## query body or URL:
POST /graphql
Body: {"query":"query { storeConfig { store_code } }"}
Header: Store: <injected PHP payload>
# Collects: kernel/OS string, PHP process user, cwd, and whether pub/media is writable
# (tracked internally as a "w_pm" flag gating whether the web-shell drop is attempted).

## Recon exfiltration — DNS-based, NOT visible in the HTTP response. Chunked (50 chars/
## label) and sent as hostname labels with a sequence index against an out-of-band
## canary domain under the oast.site collaborator service:
<50-char-chunk>-<index>.<24-char-subdomain>.oast.site
# If you have DNS query-log visibility, watch for queries to *.oast.site or similarly
# structured OOB-canary domains originating from your Magento application host — a
# backend server has no legitimate reason to be making these lookups.

## Campaign markers — the recon probe and the dropper carry a matching campaign
## identifier plus a short hex suffix, with the probe's marker sequence number one
## higher than the dropper's:
ss5_<hex>    # dropper marker
ss6_<hex>    # recon probe marker (same hex suffix as the matching dropper)
# One confirmed campaign's exact marker pair, published by Sansec — match both the
# shape above AND this literal pair, since attackers reuse infrastructure/tooling
# across targets:
ss5_457cfa2fb7    # dropper marker, exact observed value
ss6_457cfa2fb7_   # recon probe marker, exact observed value (same hex suffix)
# Treat grep hits for "ss5_" / "ss6_" followed by 10 hex characters in logs or
# recovered payloads as belonging to this second attacker's campaign, even if the hex
# suffix differs from the exact pair above — the shape is the durable signal.

## A THIRD, DISTINCT TOOLKIT (confirmed 2026-09-14) — a remote-file-include backdoor
## planted directly in a core Magento framework file, independent of both the Rust
## implant and the second attacker's pub/media web shell. See docs/VULNERABILITY.md.
## ================================================================================

## Tampered core framework file — check this against a pristine copy from the same
## Magento/composer version, not just for the cookie string below (an attacker could
## rename the cookie in a future variant; a diff against a known-good file catches any
## unauthorized edit to this file, not just this specific one).
vendor/magento/framework/App/View.php
# Detection (requires a clean reference copy — e.g. from a fresh `composer install` of
# the exact same magento/framework version, or your own pre-incident backup/VCS history):
composer show magento/framework                       # confirm the exact installed version first
# Then diff the live file against a pristine copy of that same version fetched separately
# (e.g. into a scratch directory via `composer create-project` or downloaded from
# packagist.org's source archive for that version):
diff vendor/magento/framework/App/View.php /path/to/pristine/framework/App/View.php

## Gating cookie for the framework RFI backdoor — deliberately named to look like a
## Google Analytics/Ads tracking cookie. Presence of this cookie NAME in a request is
## itself a strong signal; a matching request that also succeeds (i.e., the backdoor is
## live) additionally causes the /tmp/tmp.log write+include+unlink sequence below.
gl_google_advisor_824808
# Detection (access logs / WAF logs — cookie values are rarely logged by default, so
# this checks for the cookie NAME, which is what most default log formats do capture
# if they log Cookie headers at all):
grep -c 'gl_google_advisor_824808' access.log

## Transient artifact from the framework RFI backdoor — written, included, then deleted
## on every invocation, so it will usually NOT be present between requests. Its
## momentary existence is still worth checking for during/immediately after a suspected
## live invocation, and its absence does not mean the backdoor isn't there:
/tmp/tmp.log

## Second confirmed delivery/execution chain that does NOT require the failed-payment
## email at all — poisoning rides in the query string of a POST to:
POST /paypal/transparent/response/?<PHP source directly in the query string>
# Two distinct self-identifying payloads observed for this chain:
mgproof717.txt          # written beside the including script; a verification/proof-of-execution payload
MGPROOF::               # marker printed alongside the PHP version by the mgproof717.txt payload
MGKWSIM::               # marker printed by a direct command-execution payload
# The MGKWSIM:: payload executes whatever base64-encoded command arrives in this
# request parameter — treat ANY request containing "kwc=" against this store as a
# serious signal, not just ones you can decode and confirm are malicious:
kwc
# Detection:
grep -c 'mgproof717.txt\|MGPROOF::\|MGKWSIM::' var/log/system.log var/report/* 2>/dev/null
grep -c 'kwc=' access.log

## Database forensic queries (not StyleSmuggler-specific signatures, but standard
## places to check for persistence or injected content after any confirmed compromise
## of the Magento application user):
SELECT user_id, username, email, created, logdate, is_active FROM admin_user ORDER BY created DESC;
SELECT integration_id, name, created_at, status FROM integration;
SELECT * FROM oauth_token ORDER BY created_at DESC LIMIT 20;
SELECT config_id, scope, scope_id, path, LEFT(value,300) FROM core_config_data
  WHERE value LIKE '%<script%' OR value LIKE '%eval(%' OR value LIKE '%atob(%' OR value LIKE '%fromCharCode%';
SELECT identifier, update_time FROM cms_block WHERE update_time > NOW() - INTERVAL 30 DAY ORDER BY update_time DESC;
SELECT identifier, update_time FROM cms_page WHERE update_time > NOW() - INTERVAL 30 DAY ORDER BY update_time DESC;
